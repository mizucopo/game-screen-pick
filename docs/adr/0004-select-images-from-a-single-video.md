# Select Images From a Single Video

Issue #270 resets the product path to “game video in, blog-usable selected images out,” and Issue #271 limits the first production increment to one video. We therefore decided that the active CLI accepts one video instead of reusing the screenshot-folder selection pipeline described by ADRs 0001–0003. The old modules may remain temporarily for repository compatibility, but the video path does not call them and their scene-catalog architecture is not a constraint on this flow.

The video is sampled across its full duration. Mechanical quality and timeline distribution first reduce the frames to at most twelve times the requested output count. A configurable primary Ollama vision model evaluates those frames. Scene, visual, and timeline diversity then reduce the candidates to at most three times the output count. A configurable secondary vision model evaluates each remaining frame with its immediate before/after context so transition frames can be excluded. Final selection combines both model scores, scene diversity, perceptual-hash distance, and timeline distance; title, map, and menu screens use soft caps, while the prompt gives a small general preference to normal progression screens. No game-specific rule is encoded.

We also decided that resumability is part of the single-video result, not an optional cache mode. A run manifest binds the video fingerprint, exact sample positions, selection settings, model names and digests, prompt version, and algorithm version. Candidate frames and completed Ollama batches are written atomically below the output folder and reused only for an identical manifest. The final artifact set consists of the selected full-resolution JPEG files, `report.json`, and the human-readable `selected-contact-sheet.jpg`; a completion record hashes all of them. Ollama calls are deterministic-seeded where supported, and GPU placement is checked after each model’s first live request unless the user explicitly allows CPU execution.
