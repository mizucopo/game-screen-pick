# Migrate the Video CLI With Contract Gates

Issue [#337](https://github.com/mizucopo/game-screen-pick/issues/337) moves the active video CLI to Rust so that its users no longer manage Python, uv, venv, or Python packages. Issue [#338](https://github.com/mizucopo/game-screen-pick/issues/338) fixes the comparison baseline before implementation. This decision governs that migration; it does not assert that a Rust binary or live quality gate has passed.

## Baseline and scope

Use `e5e19c01d65cb48e9c5e1d6ccc171b4e2082228c` (1.19.4) as the executable Python oracle. The earlier issue baseline is `2799e02b1c3c5623de275aa7b02148d9b7ea6d69` (1.19.3). Their source and existing video/CLI tests are identical; dependency, template, quality and release-management changes account for the intervening diff. Record the commit, lockfile and tool versions for each comparison. The detailed source evidence, fixture locations and acceptance rules are in [the migration contract](../rust-migration-contract.md).

Port `src.main → application.run_video → VideoSelector`, both `sampled_frames` and `semantic_video`, direct Game Context, generated context, one/multiple videos, resume, reports and contact sheets. Preserve selection thresholds, weights, source/scene/time/visual diversity and deterministic ordering. ADR 0004's separate video path remains the boundary: do not port the preceding screenshot/CLIP pipeline, torch or transformers merely because those modules remain in the package.

The parent issue intentionally supersedes the provider decisions in ADR 0004, ADR 0007 and ADR 0009: use local vLLM for both image-assessment stages, video understanding and context generation; use Brave Search for generated context. Remove Ollama API/Web Search/unload dependencies and do not port OpenAI, Gemini, xAI or OpenRouter connections. Models and inference levels must be explicit in TOML, with no default. Issue #342 must establish the supported model/inference-level combinations, configuration keys, Brave free-tier exhaustion stop and search-result/context retention rules. Do not reuse an OpenAI model or inference level as a vLLM default. Direct context continues to avoid search.

Normal Rust execution must not embed Python, start Python subprocesses or invoke `uv sync`. External inference-server installation is outside that promise. Measure performance separately from equivalence: FFmpeg and live model latency are external costs, and Rust alone does not guarantee their reduction.

## Targets and external dependencies

Choose these release-validation targets from the observed use and existing CI:

| Rust target | Evidence and release condition |
| --- | --- |
| `aarch64-apple-darwin` | The dedicated Mac mini environment inspected on 2026-10-08 reports `uname -ms = Darwin arm64`, macOS 27.0 (26A428). Run contract, fault and live checks with an actual native binary there. |
| `x86_64-unknown-linux-gnu` | [.github/workflows/pr-quality-checks.yml](../../.github/workflows/pr-quality-checks.yml) and [release.yml](../../.github/workflows/release.yml) use the standard `ubuntu-latest` runner. This selects Linux x86_64 for release qualification, not proof that a Rust binary currently works. Record `uname`, image version and glibc during #344. |

Do not promise Windows, Intel macOS, Linux arm64 or musl support. The current [file utility](../../src/utils/video_selection_files.py) relies on POSIX `fcntl.flock`, `O_NOFOLLOW`, directory descriptors and same-filesystem rename; preserve their behavior on both selected targets. Do not substitute a lock that allows concurrent ownership of the same cache/output. Network filesystems are not qualified by local-filesystem tests.

Issue #344 must measure and publish the minimum macOS version, Linux/glibc requirement and actual dynamic library dependencies of each artifact. The observed macOS 27.0 environment and a moving Ubuntu runner do not establish an older OS minimum. If one target cannot pass its gates, do not advertise or ship that artifact as supported; resolve its blocker before the final migration PR.

Runtime dependencies are operator-provided `ffmpeg` and `ffprobe` in PATH, a configured local/accessible vLLM service with the selected image/video model, and Brave Search credentials/network only for generated context. Managed lifecycle or remote control additionally requires the explicitly configured finite commands and, when selected by the operator, SSH/service supervision. No implicit installation, billing, fallback provider or GPU-management expansion is introduced. The binary must carry or avoid its image-processing library requirements so users do not install OpenCV shared libraries. Font/rendering choices must pass the contact-sheet contract. Pin and report a tested FFmpeg version/codec set; do not claim all FFmpeg versions or containers work because their filename extension is accepted.

## Integration and parallel verification

Use the dedicated migration integration branch `integration/rust-migration`, initially based on `e5e19c01d65cb48e9c5e1d6ccc171b4e2082228c`, for the seven child stages. Child PRs target that branch; incomplete migration must not enter main. Only after #338–#344, independent review, target artifact checks and Human Review pass should the final integration PR target main. Preserve [CONTRIBUTING.md](../../CONTRIBUTING.md)'s release policy: do not manually bump a version in child PRs. Issue #338's documentation/fixture draft does not publish a product and requests no release label. The final intentional compatibility change requests `release:major`, with 2.0.0 as the parent issue's desired release boundary, and lets the existing controller number it.

Keep the pinned Python implementation and its package/import contract until #343 comparison and #344 deployment qualification finish. Continue `uv run task check` (whole-repository Ruff, format, strict mypy and direct pytest), with empty test collection failing. Build the Python package during this period. Add Rust quality/build/tests without removing or weakening Python gates. Only the final switch removes Python runtime/development paths from ordinary use.

Run both implementations on separate copies of the same Input Video Directory, cache and Output Folder. They must never share writable cache/output during a comparison. Store a frozen Python cache copy before importing or testing it; compare read/reuse/invalidation against that copy. Use relative Input Video Identity to compare moved copies, and normalize absolute report paths without discarding source attribution. Two copies on the same filesystem are enough; no live GPU or external API is needed for fixed-response fixtures.

Fixed-response tests compare exact candidate decisions, frame ID/time/rank, scenes, transitions, tie ordering and resume outcomes. Use the contract's predeclared numerical/image tolerances for floating point and codec/rendering differences. Cache digest vectors are byte-contract checks, while output JPEG byte hashes are verified within each implementation. Do not discard a discrepancy by regenerating golden files or broadening tolerances after seeing it. Live provider/model changes use a separate repeated same-input comparison and signed Human Review; no Ollama/vLLM response identity is required.

## Cache migration boundaries

Keep ADR 0008's filename/size Input Video Identity, stable frame IDs, visible regenerable cache, versioned semantic keys, payload integrity, ownership checks and failure protection. Language alone is not a reason to invalidate a compatible phase. Conversely, a matching filename is not sufficient evidence of compatible semantics.

| Python phase/data | Rust reuse decision |
| --- | --- |
| video identity/probe | Reuse only with unchanged identity/key version, canonical serialization, full metadata payload digest and structural checks. The same-name/same-size source replacement limitation remains documented. |
| candidate extraction/secondary context JPEGs | Reuse only if selected stream, timestamps, FFmpeg extraction/scale/JPEG conditions, frame ID, manifest and requested image checks match. A changed image-production contract bumps that phase version and its dependent keys; do not overwrite the old namespace. |
| mechanical analysis | Reuse only if decoded image, gray conversion, border handling, metrics, thresholds, score and dHash contract are proven identical, and source manifest/payload digest coverage passes. An implementation that passes output tolerance but changes stored numerical values must use a new mechanical phase version. |
| primary/secondary assessment | sampled_frames' Ollama results are not transplanted as vLLM inference. Provider/model/revision/inference-level/prompt/AI-input changes produce new semantic keys, and a new prompt or response contract bumps the corresponding version. Existing semantic_video results may be imported only if every effective inference condition, payload/prefix and image digest is identical; newly mandatory inference level must be explicitly mapped to the old deployment with evidence. No implicit mapping. |
| semantic chunks/plan | Reuse chunks only if vLLM model/revision/inference conditions, prompt/schema, Game Context and bounded media contract match. Changed plan rules bump the plan version while retaining compatible chunks; changed evidence invalidates downstream even if timestamps coincide. |
| generated Game Context | Old provider checkpoints remain available to Python. Brave+vLLM uses a new provider/schema/key namespace; do not label old searches as Brave results. Allow users to deliberately use the old final context as direct input instead. |
| run manifest/completion/report | Recompute new run metadata for new provider/settings/versions; retain old records for rollback. A legacy report can establish output ownership only under the existing schema, exact-set and integrity rules. Do not reinterpret invalid/unknown data as ownership. Produce new artifact/completion records only after successful staging/publication. |

Canonical JSON and file-body digests must match Python exactly before claiming read compatibility. If Rust cannot reproduce a phase's serialization or behavior, it must miss that phase under a new version, preserve compatible earlier phases, and record the reason in migration notes/tests. Do not delete the whole Python cache to conceal a migration failure. Shared format upgrades belong to a new schema/version with an explicit importer and regression tests; the importer must leave its source snapshot unchanged. Schema/version numbers are assigned by the implementation issue that actually changes the contract, not preemptively by #338.

## Cutover and rollback

1. Before cutover, retain the pinned Python checkout/environment or installed package, old TOML, a full cache snapshot and a known-good Output Folder with report/contact sheet. Keep credentials outside repository artifacts. Record tool/model/revision/configuration provenance.
2. Complete fixed fixture and actual-video checks for both strategies; run corruption, lock, interruption, HTTP failure and cleanup failure checks on both targets. Obtain Human Review under the contract. Test packaged artifacts in environments without Python, uv, venv or Rust toolchain; FFmpeg and the configured inference service remain present.
3. Translate old settings into explicit vLLM model/inference-level and optional Brave settings using #342's migration guide. Reject obsolete provider/Ollama keys with useful migration errors. Run Rust on a separate cache/output copy, verify report integrity and review its selected images before replacing the default executable.
4. Make the final main PR with all seven stages, target qualification evidence, cache/version changes, settings guide and release classification. After approval and the normal release controller, switch the user's CLI invocation to the qualified binary. Python cleanup happens only after the switch gate; it is not performed by #338.
5. If rollback is needed, stop all runs/lifecycle commands, restore the Python executable and original TOML and use the retained original Input Video Directory/cache/output snapshot. Do not point Python at Rust-only schemas or newly relabeled AI results. If snapshots are absent, use a fresh empty output and explicitly regenerate a separate cache with Python. Never delete an intact user output to force reuse. Preserve failed Rust output/cache for diagnosis in a separate location.

Previous completed output remains protected through probe, evaluation and staging failures. The current publication boundary is per-file atomic replacement after staging, with completion written last; it is not a transaction for the entire artifact set. A kill during publication can leave a mixed set, which must not be accepted as completed. Rust must pass those recovery tests; a stronger whole-set transaction would require a separate decision and compatibility analysis.

Unresolved implementation decisions are intentionally assigned to later stages: image libraries/font choice and measured equivalence (#340), any required phase/schema importer changes (#341), model/inference-level and Brave contract (#342), real-video quality evidence (#343), minimum OS/FFmpeg versions, linkage and actual release artifacts (#344). They are release blockers until proven, not promises made by the fixture-only first stage.
